# 引擎运行时行为学 —— 实证知识（AIPLAY 开发中踩坑验证）

> 区别于源码静态地图（另见同目录文档）：本文记录**运行时才暴露的引擎行为**，全部经过浏览器内实测验证（2026-10-01 ~ 10-03，AIPLAY v1.0→v1.7 开发过程）。
> 写自动化、调试器、或任何"从外部驱动这个引擎"的东西前必读。普通玩法开发也建议了解 §1/§3/§6。

## 1. 场景生命周期（最重要的一课）

### 1.1 官方链与排队制
- `SceneManager.goto(X)` / `push(X)` 只是排队：`_nextScene = new X()`，**真正的交接在下一帧 updateMain → changeScene()**。
- `changeScene()` 有 busy 门：`isSceneChanging() && !isCurrentSceneBusy()`。**busy 的来源不止 fade**：
  - Scene_Base：`_fadeDuration > 0`
  - Scene_Map.isBusy 额外算：消息窗 closing、`_waitCount`、**`_encounterEffectDuration`（遇敌演出）**
  - 各场景自定义 isBusy（如标题的 commandWindow.isClosing）
- **实证坑①**：GTP 的 changeScene 只调 `terminate()`，**不调 stop()**。Scene_Map.stop() 里的 `launchBattle()`（遇敌演出启动器）在 push(Scene_Battle) 路径上会处于"没人调用"状态，但 `_encounterEffectDuration` 却被置 60 无人递减 → busy 恒真 → 换场死锁。（AIPLAY battleSetup 实测，用 forceSwapScene 绕过）
- **实证坑②**：闪屏场景（Scene_SplashScreens）在启动期长期 isBusy → reset 类操作必须绕过 busy 门。

### 1.2 forceSwapScene（强制换场的安全做法）
等价复刻 changeScene 但去掉 busy 检查（AIPLAY v1.6 验证可用）：
```js
清 _fadeDuration → 旧场景 terminate() + detachReservation() → _scene = _nextScene
→ attachReservation() → create() → _sceneStarted = false → onSceneCreate()
```
之后真实主循环的 updateScene 会在 isReady 后正常调 start()。
**手动装配的边界**：直接 new + create + start() 一个复杂场景（如 Scene_Map）不可行 —— spriteset/CharacterPatterns/GALV CamControl 都依赖正规链路（三次实证失败）。但**自包含场景（Scene_UnwrittenStory 书场景）可以**，只要补 `_sceneStarted = true` 防止真实循环二次 start()（v1.6 实测：不补会重置窗口状态）。

### 1.3 updateScene 的失焦门
GTP 版 updateScene：`if (this.isCurrentSceneStarted() && !!this.isFocus()) { this._scene.update(); }`
**isFocus() 检查 window.top.document.hasFocus()，内嵌浏览器恒 false → scene.update() 被静默跳过**（表现：fade 永不递减、一切动画冻结但无报错）。浏览器测试环境必须覆写为恒真。

## 2. 主循环的真实结构

```
rAF（可见时 60fps；隐藏页签被节流至 ~1Hz 或完全挂起）
  → SceneManager.updateMain()
      → newTime = performance.now()；fTime 封顶 0.25s
      → _accumulator += fTime
      → while (_accumulator >= _deltaTime) {   // 固定步长！
            updateInputData();  // Input.update + TouchInput.update
            changeScene();
            updateScene();      // isReady→start()；isFocus→scene.update()
            _accumulator -= _deltaTime;
        }
      → renderScene() → requestUpdate()
```
- **按墙钟累计固定步长** → 重复调用 updateMain 无副作用（这是 Worker 驱动器兜底的理论基础：主循环死后用 Web Worker 的 postMessage 唤醒，updateMain 自己会算该跑几步）。
- **Scene_Map.updateMain 是另一回事**（场景层的地图/玩家更新），有独立的 `_currentTime` 真实时间门槛（见 §5）。
- 浏览器隐藏时 **rAF/setTimeout/setInterval 全部节流或挂起**；Web Worker 的 postMessage 是唯一可靠的唤醒源（AIPLAY Worker 驱动器实测：隐藏页签下维持 ~60fps）。

## 3. Input 系统实证

- `Input._currentState` **按按钮名键控**（'ok'/'cancel'/'up'/'down'/'left'/'right'/'shift'/'menu'/'control'），不是键码。OMORI 的"确定"= Z 键，但注入层与键码无关。
- **`Input.dir4` 是 getter，只在 Input.update() 时重算** —— 设完方向键必须先 Input.update() 再泵帧，否则玩家不动（v1.3 双根因之一）。
- 手动泵帧的正确顺序：**Input.update() 在 SceneManager.updateScene() 之前**（更新输入 → 场景消费输入）。
- 走一格 ≈ 32 帧（实测校准；14 帧不够）。
- 按键的"边沿"由 current/previous 状态对比产生；长按 ok 是长按语义（快进文本用）。

## 4. 数据加载实证

- `DataManager.loadDataFile` 用**裸 XHR**（无 no-store 头意识）→ 测试服务器若不发 Cache-Control，浏览器启发式缓存会咬死几天前的旧 data/*.json（实测：磁盘 2101 开关槽、游戏加载 2001 → 模组 2001+ 开关静默失效）。测试环境要 no-store 服务器 + 首载强刷缓存。
- **MV 硬限制**：`Game_Switches.setValue` 要求 `switchId < $dataSystem.switches.length` —— **越界静默丢弃，不报错**。加新开关区必须先扩 System.json 的 switches 数组。
- 地图加载：`$dataMap` 异步 XHR + Tiled 数据（DataManager._tempTiledData）→ `forceMapLoad`（同步 XHR 预载）可绕异步等待。
- `$gameMap.isReady()` 在 Tiled 装配路径下**可能恒 false** —— 等待条件用 `mapId > 0 && !isTransferring()` 更可靠。

## 5. 时间门槛与节流

- **Scene_Map.updateMain 有 `_currentTime` 真实时间门槛**（"每帧归零穿越"技巧：把 `scene._currentTime = 0` 可强制门槛立即穿越 —— AIPLAY frames() 每帧做一次，地图更新才跟得上手动泵）。
- IAB/后台标签的 setInterval 压至 ~1Hz；**同步泵帧（for 循环调 updateScene）不受节流**，但泵的序列不完整（没有 updateInputData/固定步长逻辑）→ 长链路（newGame/换图）必须让真实主循环来跑（waitFor 异步等待 > pumpUntil 忙等 —— 忙等会饿死真实循环，v1.6 教训）。
- 评测通道（evaluate）有 3 秒超时：**任何含同步长操作的调用要先 wait(1) 延迟一拍**，否则整个调用被中止（表面是 Internal error）。

## 6. 存档系统实证

- 本地模式（NW.js / node_compat shim）**全同步**：`writeFileSync` + LZString.compressToBase64 → `readFileSync` + decompress；内存 overlay shim 下 round-trip 可用。
- `loadGameWithoutRescue` 内部调 `createGameObjects()` 重建全部游戏对象再 `extractSaveContents` 灌数据 —— **读档后任何对旧对象的引用全部失效**。
- `saveGame` 前要手动 `$gameSystem.onBeforeSave()`；global.rpgsave（槽位 0）单独维护 `isThisGameFile` 判定。

## 7. 战斗运行时实证

- 命令窗 symbol：OMORI 的攻击是 **`actionSkill`**（非 attack）；`guard`→零食菜单、`item`→玩具菜单被 TDS 重绑定。
- 战斗入场动画长约 30 秒（窗口先 active 但 `_list` 为空 —— **等待条件必须含 `_list.length > 0`**）。
- 敌选择窗激活瞬间 `_list` 可能为空：直接 `select(0)+processOk()` 有效。
- `BattleManager._phase` 状态机实测值：init → start → input（inputting=true，party/actor 窗激活）→ actionList（**ACS 追击 120 帧方向键窗口，不按则自动过**）→ actionTargetList → turn … busy='animation' 期间无窗口激活。
- push(Scene_Battle) 会触发 §1.1 坑①的 encounter 死锁 → forceSwapScene 可靠。

## 8. 窗口（Window）层实证

- 活跃窗口判断：`w.active`；命令表 `w._list`（{symbol, name, enabled}）。
- **程序化选择**：`w.select(idx); w.processOk();` 等价玩家按 ok（OMORI 自定义窗口链也走得通），比注入按键稳。
- 手动调 `scene.start()` 是危险操作（会重置窗口/状态，仅诊断用）。
- `assemble()` 手动装配场景后必须 `SceneManager._sceneStarted = true`，否则真实循环 updateScene 会再 start() 一次。

## 9. 调试钩子（AIPLAY 沉淀的四层错误捕获）

1. `window.onerror` + `unhandledrejection`（最早挂，防 load 前盲区）
2. console.error/warn 劫持（带 Error.stack 首三帧）
3. `SceneManager.catchException/onError` 包装（引擎崩溃处理器）
4. `Graphics._makeErrorHtml` 包装（屏显错误的原文）
配套：`__bootlog` 环形缓冲（200 条）+ 立即挂载 + 250ms 轮询兜底（防脚本顺序意外）。
**注意**：Worker 驱动器的 onmessage 里 try/catch 会吞掉 updateMain 的异常 —— 排查"游戏悄悄冻结"时先查 __bootlog 有无被吞的错误。

## 10. 浏览器环境的特殊处理清单（ai_test.html 现行方案）

| 问题 | 方案 |
|---|---|
| rAF 挂起（隐藏页签） | Worker 驱动器（启动即装，不依赖检测） |
| isFocus 恒 false | 启动即覆写 `SceneManager.isFocus = () => true` |
| data/*.json 启发式缓存 | 首载 `fetch(..., {cache:'reload'})` 全量强刷 + 自动 reload 一次（sessionStorage 防循环） |
| 出声 | `?muted=1`：AudioManager 播放入口空操作化（playBgm 等 6 函数），v2 根治 2 秒漏音窗 |
| node API（fs/require） | node_compat.js shim：fs 走 XHR/内存 overlay、require 模拟 |
